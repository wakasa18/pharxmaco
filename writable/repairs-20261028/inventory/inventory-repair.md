# Selected inventory repairs, 28 October 2026

Selected scope A02/A03/A04/A06 is implemented locally. No application database, SQL, service or hosted deployment was changed. A05 ordinary date-only product-edit policy was explicitly excluded and remains unchanged.

- A02: refund IDs must be canonical, positive and unique; normalized entries are keyed before becoming a list. Distinct IDs are recalculated under the sale lock, and the aggregate payout cannot exceed the saved invoice net less prior payouts. Invalid/aliased IDs produce no refund, stock or movement write. Canonical retry cannot duplicate.
- A03: ordinary resellable refunds use original sale delivery/expiry through StockExpiryProvenance under the inventory lock; quantity correction increases/decreases also require a known, matching, future-expiry source. Legacy unknown/expired/mismatched returns can be Quarantined, Damaged or Expired without adding available stock. Refund form disables unsafe Resellable and explains why; a stale old selection falls back to Quarantined. Existing helper already enforced these rules and required no edit.
- A04: new product/branch creation and catalog assignment set fresh source IDs. Quantity increases by Product Edit, count or Add stock rotate identity; replacements rotate even when quantity/expiry are identical. Removals/decreases retain identity. Replacement revisions include delivery identity. BranchProductModel allows the field; its omission previously stripped source assignments. No historic snapshot backfill.
- A06: unused legacy receive mode is rejected explicitly. Modern Add/Remove keep their one-time session token and locked old_stock checks; absolute counts keep their locked revision. An identical Add or Count replay makes no second mutation. No new SQL/idempotency table is introduced.

Validation:18 new tests /106 assertions pass. Expanded affected inventory/refund/quarantine selection:41 tests /320 assertions pass. Evidence focused.xml and affected.xml. These checks use in-memory SQLite and real controller/service paths. A later bounded real-MySQL concurrency pass is recorded below; it uses synthetic scratch data only. The root agent owns full-suite results, checkout and exchange changes and final bundle manifest.

Runtime files: Products.php, Admin/SaleCorrection.php, refundForm/refundPartial sections only of Cashier/SalesController.php, ExpiryStockResolution.php, BranchProductModel.php and refund_partial.php. Added tests/unit/InventoryRepairCases.php; root wires the trait into BusinessLogicTest.php.

Remaining limits: existing single-current-delivery inventory cannot represent simultaneous batches. Receiving additional units conservatively invalidates older return matching for the combined inventory; do not infer full lot tracking. Date-only Edit Product remains the explicitly unselected A05 policy. Existing historic unknown source/expiry data is preserved and cannot be reconstructed. No actual-data repair or hosted verification performed.

Final locking pass: after the sale lock, existing refund rows are read once with ORDER BY id FOR UPDATE and aggregated per item/invoice in cents. All post-lock quantity, payout and final-status checks use those current balances; no ordinary refund aggregate is consulted after waiting for the sale lock. Final sale-item quantities use a locking read. Three new lock-hook cases cover a competing prior refund, cumulative invoice ceiling and exact last-refund status. SQLite proves the lock-query path and business results; it does not emulate MySQL concurrent scheduling.

## Synthetic real-MySQL concurrency verification

The final mysql-concurrency.php harness uses MySQL 8.2.0 / REPEATABLE-READ with two workers, separate synthetic administrator accounts/open drawers/shifts and an explicitly established pre-lock snapshot in each worker. It creates its own guarded random schema, never connects to/selects/copies the application database, and removes only its verified scratch schema on completion. No services were started.

Both workers request three returned units from a five-unit sale: exactly one commits, the other receives the changed-refundable-quantity error. Final totals: one refund, three units, PHP30, branch stock13 from10 and one returned-stock log. Two matching Add-five requests against old_stock10 likewise produce one increment to15 and one movement; the other receives a stale-balance rejection. These exercise real controllers, current locking refund aggregates and stock revision checks with actual InnoDB transactions.

Evidence: mysql-concurrency.json and guarded harness script. The initial harness incorrectly required a refund success flash (this controller does not set one); its database result was already safe. The acceptance criterion was corrected to actual persisted counts plus response/error outcomes. Final two scenarios passed; schema_removed=true. This does not verify every MySQL schedule, other DB versions or hosting.
