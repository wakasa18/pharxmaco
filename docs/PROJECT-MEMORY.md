## Keep these distinctions

1. **Local versus hosted:** an applied local repair is not evidence that Hostinger was changed. SQL prepared for phpMyAdmin still requires an import on the intended host.
2. **Code versus database:** the presence of a migration or patch does not prove it ran. Check the selected database and its migration history.
3. **Historical versus current:** dated reviews preserve findings at the time. Follow repair reports and record fresh evidence when closing an issue.
4. **Operational limits versus bugs:** multiple manufacturer lots, prescription dispensing, payment-provider settlement and full accounting are outside the current implemented workflow.
5. **Partial tests versus whole-suite status:** the last recorded full suite had twelve unsuccessful inventory/expiry checks. Later focused passes do not close them.

## Before continuing implementation

Read [Known issues](project/Known-Issues.md), inspect the current relevant code, and identify the intended branch/database or package. Keep completed-sale values and existing backups intact unless a specifically scoped data change is authorized. Never infer an old medicine delivery from today's stock balance.

Record the completed change, its validation, any unresolved condition, and the next step in a [handover note](templates/Session-Handover.md). Update the current-state and decision notes when the behavior changes. Run the documentation sync and link check after adding or moving notes.
